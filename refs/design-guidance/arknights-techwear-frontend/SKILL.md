# Arknights Techwear Frontend

将《明日方舟》的档案式信息编排、《明日方舟：终末地》的工业导视与空间层次，以及机能服装的可达性、模块组织和功能外显，转化为可用的前端。先形成内容骨架，再让视觉表达骨架。

这些是依据公开官方页面与产品资料归纳的设计方法，不是官方设计规范。颜色、比例、断点和时间参数均为本 skill 的建议值；不要声称是官方 token。来源和观察范围见 [references/sources.md](references/sources.md)。

## 先选择方向

沿用任务指定的技术栈、产品用途、内容和品牌约束。对现有产品，先检查样式与组件入口，尽量通过 token 和少量布局调整实现目标。新项目未指定框架时，选足够完成任务的最小方案。

根据使用场景选一个主方向，并用一两句话说明取舍；无需逐项询问用户。

| 方向 | 更适合 | 主导语法 |
| --- | --- | --- |
| Archive / 档案 | 资源目录、研究工具、作品档案、密集数据 | 深墨色底，清晰分栏，窄体大标题，青色导航信号，索引与细分隔线 |
| Field / 工业 | 工具工作台、制造/地图/空间类产品、清爽展示 | 纸白或浅灰底，深色字，黑黄导视，侧向索引，大留白与强结构线 |
| Hybrid / 综合 | 希望兼顾阅读、内容展示与工具感 | 一种模式做主体，仅在导航、选中模块或媒体区域借用另一种；以一致网格和字阶统一 |

不要机械按比例混色，也不要认为两作永远只有一个配色。活动海报、角色图和实际游戏界面有不同语境。若任务要求某个游戏内页面或具体活动的高保真复现，应先查看该页面的用户参考或官方素材；不要用官网推断所有游戏 UI。

确定方向后读 [references/design-system.md](references/design-system.md)。进行组件编码或审查时再读 [references/frontend-patterns.md](references/frontend-patterns.md)。只有需要追溯研究或新增设计结论时才读 sources。

## 构成的关键

- **网格先于装饰。** 标题、列表、媒体边缘和工具栏共享基准线；用少数宽窄不等的区域制造主次。避免把一切包成同尺寸卡片。
- **尺度差制造视觉张力。** 展示区可以用一个很大的标题或媒体主体，操作区维持稳定字阶。正文保持正常宽度和舒适行高，窄体只用于短标题、编号等。
- **中性色承载内容，信号色指向动作。** 先把选中、焦点、错误、警告的含义分开，再分配青色或黄色。黄色背景配深色字；浅底上的黄色小字通常不合适。
- **机能结构应对应真实功能。** 导航像导轨，工具栏像附件位，侧栏像可展开口袋，分隔线像接缝；模块的边界应反映任务关系、可收起区域或操作范围。
- **装饰有限且有位置。** 微网格、网点、斜纹、切角、标记线和大字底纹只在空白边缘、媒体区或结构节点使用。不要让每个组件同时拥有这些元素。
- **画面可以大胆，操作必须稳定。** 不照搬官网的滚轮劫持、不可跳过加载或游戏 HUD 的小字。列表、表单和长文仍使用正常文档流。

## 从设计推进到实现

先列出本页的主要任务、核心内容、主动作和必要状态。对一个具体页面通常只需一个简短的布局决定和 token 集合，不必先造一套完整设计系统。

1. 用真实或明确标示的示例内容搭出结构，验证窄屏阅读顺序。
2. 建立表面、文字、边框、强调、状态、字体和间距 token，先完成标题和主工作区域。
3. 实现任务中存在的组件与交互状态，再添加少数图形细节。用 CSS/SVG 画结构性图案，不为线条和切角生成位图。
4. 在宽屏与窄屏检查实际界面，并至少走通主操作与键盘路径；按项目现有要求运行检查。无法运行时明确限制。

可选起点：[assets/tokens.css](assets/tokens.css) 提供三种方向的语义变量与少量基础样式；[assets/specimen.html](assets/specimen.html) 是无依赖的资源目录示例，可切换方向、过滤和查看详情。它们是说明材料，不是必须整页复制的模板，也不是项目的新依赖。采用时应映射到现有框架并裁去不需要的部分。

## 完成前的取舍检查

- 主任务能否在没有纹理和装饰的情况下成立？若不能，先修结构。
- 强调色是否确实标出动作或状态？移除伪坐标、随机编号、虚构状态和重复双语装饰字。真实编号与有用分类可以保留。
- 大标题、媒体和工具区是否形成明确主次？避免只换黑黄配色，其余仍是通用圆角卡片网格。
- 正文、次要文本、边框与焦点是否达到所需对比度？装饰不能承担唯一状态信息。
- 切角或 overflow 是否裁掉焦点环、菜单和长内容？窄屏能否使用筛选、详情、提交等必要操作？
- 选中、禁用、加载、空结果、失败等实际需要的状态是否可理解？是否支持减少动态效果？
- 新 UI 文案默认使用简洁英文，除非用户指定其他语言。保留必要标签、单位与错误说明；不因对话使用中文而自动写中文 UI。
- 移除没有帮助用户识别、判断或操作的可见文案，以及为填满画面添加的图形。保持必要的可访问名称。

交付时简要说明所选方向、关键行为、实际验证和限制。不要在产品 UI 中塞入本 skill 的研究过程或实现说明。
